<h1 align="center">致下一个失忆的自己</h1>

<p align="center">记忆日记（astrbot_plugin_memory_diary）· AstrBot 插件</p>

让 AstrBot 连接的 AI 在收到指令时，给"下一个失去记忆的自己"写一篇日记；
开启新上下文（`/reset`）后，第一句正常对话时她会自动先读**最近 7 天**的日记（范围可调），不再脑袋空空。

内置**上下文哨兵**：每次请求前估算上下文 token 占用，快满时主动提醒你，再满一点她会自己把日记写好，叫你去 `/reset`。

> 当前插件版本 **v0.5.5**；日记数据格式为"按天归档 v3"。插件版本和数据格式版本不是同一个东西，升级时旧格式会自动迁移。

## 1 三种写作模式

日记**按天归档，一天一个文件**（数据格式 v3）：当天写多篇会追加在同一天的文件里，用时间分隔条隔开，
不会出现"一天几十篇"的碎片化；每次写日记记录的是"上一篇日记到现在"这段时间的事，不做全文合并——
日记体积随时间可控，不会因为越攒越大而吃爆上下文。

| 模式 | 触发条件 | 写什么 |
| --- | --- | --- |
| 完整日记 | `/日记 完整`；第一次写日记；哨兵到自动写阈值时自动写；或每天定时自动写（配置开启） | 完整的四部分日记（见下一节），作为跨会话质量锚点。会把**同一场景**之前未吸收的简记作为素材合并 |
| 当天简记 | 默认 `/日记`；`/日记 简记`；或完整篇名额已满时的自动降级 | 只用 1~3 句简略概括新增内容，不占完整篇名额，追加在当天文件里 |
| 她的日常随笔 | 距上次写日记**一句话也没聊过** | 不编造用户言行，改写她（AI）自己的拟人生活：看到了什么、做了什么、想了什么；带"无新对话·她的日常随笔"标注。可在配置"无新素材时写拟人日常"关闭 |

**"完整"不是"当天第一篇"的同义词，而是"质量锚点"**：

- 默认命令先写简记，不浪费素材；
- 用户觉得这段时间重要，发 `/日记 完整`；
- 第一次写日记默认完整，给新用户一个初始锚点；
- 哨兵到自动写阈值时写完整；每天定时自动写也会写完整（当天已有完整篇则跳过）；
- **不建议多写完整篇**：完整篇是“质量锚点”，用于沉淀画像与评价，日常小更新用简记即可；
  默认每场景每天上限 1 篇，配置页里可以调整，但强烈建议不要设多。
- 完整篇写完后再写简记，简记不会反向合并进完整篇。

**已吸收标记**：完整篇会吸收同一场景之前的简记：旧简记原文保留，但分隔条会标记"（已吸收）"，
注入时跳过，不会重复占 token。跨场景暂不合并：私聊吸收私聊，群聊只吸收群聊
（当前群与群仍算同一个场景，不按具体群隔离）。

**场景标注**：每个日记片段的分隔条都带"写于私聊 / 写于群聊"标注，注入时按会话场景过滤
（详见「配置项与多用户隐私」的群聊注入过滤）。

**素材游标**：判断"有没有新内容"靠素材游标（记录上次写到哪里），不是整段素材哈希：
下次只读游标之后的新消息，避免多篇日记反复读同一段历史。游标失效（reset、历史被压缩）时
回退最近 N 条，并在写作提示里注明可能重叠。

哨兵**自动写**不会触发"日常随笔"——没新素材时不写日记，但会明确提醒你
"上下文快满了、这轮没新内容、建议 /reset"，绝不静默。

## 2 正式日记的四个部分

每篇**完整日记**必须依次包含四个部分——这是本插件最核心的记忆结构，**功能与顺序固定**，
只有小标题由她按人设自由起名：

| # | 部分 | 写什么 | 为什么是卖点 |
| --- | --- | --- | --- |
| 1 | **时间范围** | 这篇日记覆盖的起止时间，结合"当前时间"与对话里能推断出的时间线 | 下一个"失忆的自己"能立刻对齐时间线，知道这段记忆从哪到哪 |
| 2 | **用户画像** | **拟人化观察，不是填表**：像人观察熟悉的朋友那样，用第一人称自然写注意到的东西——称呼、说话做事的方式、性格里的小矛盾、最近的处境与心事、在意的东西、让她意外或记住的瞬间（挑最鲜活的几点写透，不必面面俱到）。**必须是连贯段落，不得写成项目符号或编号列表** | 记住的是"你这个人"，不是通讯录字段；换上下文后她仍能自然认出你、接住你的状态 |
| 3 | **她的评价与感受** | 她（AI）以第一人称写的真实印象、感受与评价，真诚、不客套 | 记忆带温度与立场，不是数据库快照；这是"她"而不是"检索结果"的关键 |
| 4 | **给未来的叮嘱** | 希望下一个自己延续什么、注意什么、避免什么 | 把"怎么继续对你好"交接下去，避免重置后从零摸索或重蹈覆辙 |

> **关于「用户画像」**：它不是字段清单，也不是用户档案。提示词明确要求她像人类观察一个熟悉的朋友那样，
> 用第一人称自然地带出细节与感受（语气、习惯、在意的事、最近的心事……），挑最鲜活的几点写透；
> **并且禁止写成项目符号/编号列表或「字段名：值」的档案格式——画像必须是连贯的自然段落**。
> 同时必须基于对话中真实出现过的信息，不得编造。这样换到新上下文后，她读到的是"一个她认识的人"，
> 而不是一份"姓名/性格/偏好"的表。

**v0.5.5 起，小标题由她按人设自己起**：写作提示词只说死四个部分的功能与顺序，
每个部分的标题名称由她用自己的人设口吻起一个简短、看得懂功能的名字——
温柔的 AI 可能写「这段日子的轮廓」，元气的 AI 可能写「给你的小档案！」。
不要求每篇日记的标题统一；`/reset` 后的她读日记时，注入文本里会附带一句
"小标题依次对应：时间范围 / 用户画像 / 你的评价与感受 / 给未来的叮嘱"，保证读得懂任意标题。

> v0.5.5 之前的日记使用固定标题【涵盖时间】【用户画像】【我对用户的看法与评价】【给未来的我的叮嘱】。
> **新旧两种标题都是合法日记**：插件不解析章节标题（只认时间分隔条），旧日记照常读取、注入、迁移。

四个部分之间会自然穿插她自己的"私人生活"片段——心情变化、等待你回复时的小思绪、
灵光一闪的想法、想吐槽的瞬间——像人类日记一样有"人味"。
但涉及你的事实与画像永远基于真实对话，不编造。

### 2.1 新会话如何读日记（注入的时机与效果）

- **默认（临时模式）**：每个新会话的第一轮 LLM 请求注入一次，注入文本是临时消息、不进会话历史——
  所以她**只在生成第一条回复时**"记得"日记细节，后续轮次只剩她自己回复里带出来的印象。
  省 token，适合大多数场景。
- **注入持久化（配置开启）**：每轮请求都把日记放进 system prompt，她全程都能回忆日记内容；
  代价是每轮都消耗日记的 token。在乎"她全程记得"就开，在乎 token 就关。
- **`/注入日记` 追加注入**：自动注入之后还想让她读别的日记，用这个指令指定范围，
  下一句正常对话时一次性带入；**本会话已经注入过的篇目自动去重**——重复下指令不会让她重复读同一篇，
  没有新篇目时会直接告诉你"都读过了"。多篇日记同时存在于同一轮请求时，
  以"当前对话 > 日记"的优先级规则相处，不冲突。
- 没有日记可注入时静默：不提示、不耗 token，她像没装插件一样正常开始新对话
  （zip 或某个条目 CRC 损坏时，`/查看日记`、`/日记状态`、`/注入日记` 会明确提示）。

## 3 上下文哨兵

- 占用 ≥ **提醒阈值**（默认 75%）：提醒一次"快到写日记的时候啦"
- 占用 ≥ **自动写日记阈值**（默认 90%）：自动写一篇新日记（用她的口吻告知你，不贴全文），并提醒 `/reset`
- 每个会话各触发一次，`/reset` 后重新计数
- **v0.5.5 起没有独立开关**：两档阈值滑条下限都是 0——提醒设 0 表示不提醒，自动写设 0 表示不自动写，
  两档都设 0 即整个哨兵停用。旧配置的"启用上下文哨兵 = 关"会被自动当成两档 0 处理（记一次迁移日志）：
  旧键 `enable_context_watch` 现在只在配置页「杂项」组保留一个「已废弃」兼容项，用来接住 v0.5.4 及更早的旧配置，
  平时不用管它（想重新启用哨兵就改成 true，再去调上面两档阈值）。

> 注意：请在配置里把"模型上下文窗口"设成你实际模型的上限（如 DeepSeek-V3 填 60000），
> 并确认 AstrBot 的"最大上下文消息数"没有设得太小，否则历史可能在到阈值前就被 AstrBot 自己截断。
> 提醒阈值应 ≤ 自动写日记阈值；配置颠倒时插件会自动截断提醒阈值并记日志，不会报错崩溃。

**阈值怎么设（经验值）**：

| 你的习惯 | 提醒阈值 | 自动写阈值 |
| --- | --- | --- |
| 默认推荐 | 0.75 | 0.9 |
| 聊得长、日记内容多 | 0.7 | 0.85 |
| 只想保险、不想被打扰 | 0（不提醒） | 0.9 |
| 完全手动管理 | 0 | 0（哨兵停用） |

**token 是怎么估算的（v0.5.5）**：

- **改进版估算（实验性功能，默认关闭）**：按字符类别加权——中文等 CJK 字符 ×0.8、英文等 ASCII 字符 ×0.25、
  其他字符 ×0.33，外加每条消息 +3 的包装开销、工具 schema 字符数 ÷4、每张图片 ×1024、每段音频 ×200。
  旧公式"字符数 ÷1.8"对中文系统性低估（中文实际约 1~1.5 字符/token），会导致哨兵触发偏晚；
  关闭「改进版 token 估算」可完全回退旧公式。
  注意：图片 ×1024、音频 ×200 是代码里的**固定保守值常量**（`IMAGE_TOKEN_ESTIMATE` / `AUDIO_TOKEN_ESTIMATE`），
  **不是面板配置项**（面板里没有对应开关）；要调整只能改源码。
- **自动校准（实验性功能，默认关闭；仅改进版下生效）**：每次请求后，插件拿服务商返回的真实 token 用量
  与本次估算做 EWMA 平滑（新系数 = 旧系数 ×0.8 + 实际/估算 ×0.2，钳制在 0.3~5.0，
  异常样本自动跳过），随使用自动收敛，无需任何手动设置。估算值按真实请求校准（含本轮注入的日记），
  所以越用越接近服务商的真实计费数字。
- **两个实验性开关的关系**：两个都开 → 自适应校准（采样 → EWMA → 写 `token_calibration.json`）；
  只开改进版 → 只有静态分类估算（系数恒 1.0）；关改进版 → 校准整体不生效（回退旧公式、不采样、系数 1.0）。
  关闭开关**不会删除**已有校准文件，重新开启会继续沿用其中系数；想从 1.0 重学请删除文件并重载插件。
  哨兵阈值本身不受这两个开关影响，只是估算可能偏早/偏晚。
- **校准数据存哪**：插件数据目录下的 `token_calibration.json`，按 `provider::model` 分别记录
  `factor`（系数）、`samples`（样本数）、`last_actual`（上次实际值）、`updated`（更新时间）——
  **只存数字系数，不存任何聊天内容**。其中 `last_actual` 是**实现补充字段**：方案原文只要求
  `factor`/`samples`/`updated`，但 `/日记状态` 要显示"上次实际"就必须把它落盘。
- **观测**：`/日记状态` 在改进版下显示"当前上下文：估算 X / Y tokens（Z%）"，
  这个数和哨兵判定用的是同一个数（复用最近一次请求的估算），所以状态页和"什么时候会提醒/自动写"
  永远一致；有校准样本时再附一行"校准：上次实际 …（系数 …，样本 …，provider::model）"。
  它是**估算值**，与真实计费存在 ±15% 左右的误差属于正常，校准会随使用慢慢缩小它。

## 4 每天定时自动写完整日记

在配置页打开「每天定时自动写完整日记」并填一个时间（`auto_diary_time`，默认 `22:00`，按「日记时区」计算），
插件会在每天到点时，给**有过私聊会话的用户**自动写一篇**完整日记**（等同 `/写日记 完整`）：

- **当天已写过完整日记就跳过**：只要当天已有任意完整篇（私聊或群聊场景都算），到点不再写；
- **没有新素材就不写**：距上次写日记没有新聊天、也没有当天未吸收的简记时，静默跳过
  （不会写"日常随笔"，也不打扰用户）；
- **每个用户每天只尝试一次，失败不重试**：写完会按人设口吻主动私聊告知
  （配置「人设口吻」关闭时用固定文案）；写入失败只发一次固定技术说明，让用户知道可以手动 `/日记`；
- **只对私聊用户生效**：写和通知都走私聊，群聊会话不参与。用户表会在插件启动时从 AstrBot 现有私聊会话补齐，
  之后每次私聊消息也会自动登记；从没和 bot 私聊过的用户不会收到自动日记；
- **受白名单约束**：填了「允许使用插件的用户」后，名单外的用户不会被登记、也不会被到点触发
  （管理员收紧名单后无需重启，即时生效）；
- **错过不补写**：到点时 bot 必须在线；启动/重启比设定时间晚 **2 分钟以内**会补触发一次，超过就当今天错过、等明天；
- 自动写与手动 `/日记` 共用素材游标、备忘吸收、完整篇名额等规则；它不占用"日记操作间隔"，
  也不受「手动写日记的最低上下文占用」门槛限制，不需要 `/reset`；
- **成本提示**：到点会给每个登记用户各尝试一篇完整日记——有素材的用户会调用一次模型写日记；
  若「人设口吻」开启，成功/失败通知还会各多一次调用。用户多的实例请评估 token 消耗；
  没有新素材的用户会在调用模型前跳过。

### 7.2 群聊多 AI 防冲突（v0.5.5 起简化）

| 写法 | 效果 |
| --- | --- |
| `/写日记` | 广义指令：所有装插件的 AI 都会响应（适合只有一个 AI 的群） |
| QQ 自带@ + 指令 | 点名指令：只有被@的那个 AI 响应，其他 AI 保持沉默 |

#### 7.2.1 点名规则

- @请用 **QQ 自带的@功能**（At 组件带 QQ 号，精确比对，最可靠）；
- **指令 token 内出现文本形式的 @，一律视为"在叫别人"、保持沉默**（例如连写的 `/写日记@小深`）。
  v0.5.5 起不再维护"我的称呼"名单：插件只检查指令本体（第一个空白前的 token），手敲名字无法点名；
- 指令里 **@了别人**（其他 AI 或群友）时，她会判断"不是叫我"，完全不响应、不抢话；
- **参数内容里的 @ 不影响响应**：`/记一下 记得@张三 他下周考试` 里的 `@张三` 是要记的内容，
  它不在指令 token 内，插件不会把它当点名，她照常响应并记下；
- 开启"群里只响应@我的指令"后，连不带@的广义指令也会无视——多 AI 群建议每个实例都开启；
- 私聊不受任何限制，永远响应；
- 注意：请把@放在指令后面，放在指令前面可能不会被识别为指令。

## 8 配置项与多用户隐私

**以下内容（第 8～14 节）为管理员向。** 配置全部在 WebUI 插件配置面板修改；
面板按本节 8.1 → 8.11 的分组顺序渲染，每个配置项与下文逐条对应（8.2～8.4 是判读/排障说明，
没有对应配置项；已废弃的旧键在「8.11 杂项」组第一条）。

### 8.1 上下文哨兵

- **模型上下文窗口（tokens）**：默认 60000，按你的模型实际上限填（如 DeepSeek-V3 填 60000），
  用于把占用换算成百分比。**填 0 或负数 = 停用上下文哨兵**（提醒、自动写日记、`/日记状态` 的百分比、
  手动写日记的比例门槛一并停用）。
- **提醒阈值（占比，0=不提醒）**：默认 0.75，滑条 0~1。占用到该比例时提醒一次。
- **自动写日记阈值（占比，0=不自动写）**：默认 0.9，滑条 0~1。到该比例自动写好日记并提醒 `/reset`。
  两档都设 0 即哨兵整体停用；提醒阈值应 ≤ 自动写阈值，颠倒时自动截断并记日志。
- **改进版 token 估算（实验性功能，默认关闭）**：开启后按中文/英文/代码分类加权并计入图片、工具开销；
  关闭回退旧公式（字符数÷1.8）。
- **token 估算自动校准（实验性功能，默认关闭）**：仅上一项开启时生效。开启后按服务商返回的真实 token 用量
  自动修正估算系数（EWMA），存 `token_calibration.json`，只存数字系数。
- **两个实验性开关与校准的关系**：两个都开 → 自适应校准；只开改进版 → 静态分类估算（系数恒 1.0）；
  关改进版 → 校准整体不生效（旧公式、不采样）；关闭开关不会删除已有 `token_calibration.json`，
  重新开启会继续沿用（想从 1.0 重学请删除文件 + 重载插件）。哨兵阈值本身不受这两个开关影响。

### 8.2 上下文哨兵：阈值与自动估算的关系（判读指南）

**一句话**：管理员配置决定"线"（什么时候该提醒/该写），自动估算只负责"读数"（现在到哪了）。
估算和校准**永远改不了、也不会覆盖你设的阈值**。

#### 8.2.1 判定公式（每次 LLM 请求前执行）

```text
分母 limit = context_token_limit             ← 你填的模型上下文窗口（tokens）
分子 used  = 静态估算 E × 校准系数 factor     ← 插件自动计算
占用比例    = used / limit
ratio ≥ auto_ratio    → 自动写日记
ratio ≥ remind_ratio  → 提醒
```

`limit × 阈值` 就是绝对 token 门槛：例如窗口填 60000、阈值 0.75 / 0.9 → 提醒线 45000 tokens、
自动写线 54000 tokens。每次请求的估算 E 包含 system prompt、历史消息、工具 schema、图片/音频等
（「改进版 token 估算」开启时的分类加权；关闭则回退旧公式"字符数÷1.8"）。

| 你 / 插件改什么 | 影响"线"（阈值、窗口） | 影响"读数"（used） |
| --- | --- | --- |
| 改提醒阈值 / 自动写阈值 | ✅ 立即改变触发点 | ❌ |
| 改模型上下文窗口 | ✅ 改变两条线的 token 数与百分比 | ✅ 百分比的分母 |
| 插件自动校准（按 `provider::model`） | ❌ 完全不动阈值 | ✅ 修正估算偏差 |
| 换模型 | ❌ 不自动改阈值/窗口 | ✅ 新模型有独立系数，从 1.0 重新积累 |
| 关「改进版 token 估算」 | ❌ | ✅ 回退旧公式 |
| 关「token 估算自动校准」 | ❌ | ✅ 系数恒 1.0（纯静态估算） |

#### 8.2.2 几个容易误解的点

- **换模型不会自动调整哨兵**：窗口需要你手动改成该模型的真实上限；阈值仍是你在配置页设的百分比。
  唯一"自动"的是校准系数——按 `provider::model` 分开学，只修正"估算 vs 真实用量"的偏差。
- **哨兵停用不影响校准学习**：两档阈值都设 0（哨兵停用）时，只要「改进版估算 + 自动校准」两个实验性开关都开着，
  插件仍会采样学习，以后重新启用哨兵时系数已经收敛。
- **改进版估算开启时三处同口径**：哨兵判定、`/日记状态` 的「估算 X / Y tokens（Z%）」、
  手动 `/日记` 门槛（受「手动写日记的最低上下文占用」限制）用的是同一个 `used`，
  不会再出现"哨兵说该写了、状态页说没满"。
- **窗口填 0 或负数 = 停用比例体系**：哨兵判定、`/日记状态` 的百分比、手动写日记的比例门槛
  都会停用（状态页会明确标注"哨兵与比例门槛已停用"）；想只关哨兵也可以把两档阈值都设 0。
  窗口缺省/非法值仍按默认 60000 处理。

#### 8.2.3 估算偏早/偏晚怎么调

优先调阈值或窗口（立即生效、可预期）；校准只负责让百分比更贴近服务商
真实计费，不改变你定的触发点。想量化偏差，可按 `/日记状态` 的校准行记录估算与实际的比例。

### 8.3 校准系数出问题了怎么办？

#### 8.3.1 正常表现

每个 `provider::model` 的系数会稳定在"真实用量 ÷ 估算用量"的比例上
（夹在 [0.3, 5.0] 之间），样本越多越稳；单次样本比例超出 [1/10, 10] 视为异常直接跳过；
不同模型/服务商各存各的记录，互不影响；`token_calibration.json` 最多保留最近 64 个 key，只存数字。

#### 8.3.2 可能出问题的信号

- 系数长期贴在上限 5.00 或下限 0.30 → 哨兵会明显偏早/偏晚（`/日记状态` 的校准行可直接看到）；
- `/日记状态` 显示的系数与文件里的数值不一致——显示会按 [0.3, 5.0] 钳制，文件里的值可能被手动改过；
- `token_calibration.json` 损坏/手改坏 → 插件记一条 warning 并当作空表重置，不会报错中断。

#### 8.3.3 处理步骤

1. **先定位是哪个模型**：看 `/日记状态`「校准：上次实际 …（系数 …，样本 …，provider::model）」，
   或直接打开数据目录的 `token_calibration.json`（只含 `factor`/`samples`/`last_actual`/`updated`，
   没有任何聊天内容）。
2. **只想让某个模型重新学**：先在 WebUI 重载插件 → 删除该 key（或删除整个文件）→ 下次请求从 1.0
   重新积累。⚠ 插件运行中会把系数缓存在内存里，直接在跑着的时候改文件可能被旧缓存覆盖，
   所以务必"重载后再改，改完再重载"。
3. **不想让它自动学**：配置页关闭「token 估算自动校准」→ 系数恒 1.0（纯静态估算）；
   再关闭「改进版 token 估算」则回退旧公式，行为与 v0.5.4 一致。
4. **想彻底恢复出厂估算**：删除 `token_calibration.json` + 重载插件即可（factor 全部回到 1.0）。
5. 若系数反复贴边、且确认不是早期样本太少导致的：多半是服务商 usage 口径异常
   （例如某些请求不返回或重复计入缓存 token），建议关掉校准并带上日志反馈，不要靠手改系数硬撑。

### 8.4 校准出问题会影响已经存下来的日记吗？

**不会。** 校准只影响"上下文占用比例"这个数字（触发时机与状态页显示），不参与日记的生成以外的任何存储：

- 不改日记正文、不改 `diary_*.zip`、不改 `sigs/*.sig` 签名、不改 `.diary_key`、不改备忘与偏好文件；
- 最坏结果只是**触发时机**变化：系数偏高 → 提醒/自动写来得早，偏低 → 来得晚；
  日记仍然正常生成、正常签名、正常落盘，内容与存储格式不受影响；
- 自动写若当天该场景的完整篇名额已满，会按规则**降级为简记**（哨兵到点必须留下记忆），
  不会破坏"每天最多几篇完整日记"的配额；
- 删除或损坏 `token_calibration.json` 的后果只是回到纯静态估算（系数 1.0），日记文件不受任何影响；
- 真正的日记数据风险（zip 损坏、手改导致验签失败、主密钥 `.diary_key` 丢失）与校准无关，
  见「11 日记存储位置与提取」和「13 故障与恢复」。

### 8.5 新会话读日记（注入）

- **新会话自动读取日记**：默认开启。关闭后只写日记、不自动注入。
- **默认注入最近几天的日记**：默认 7 天；0 表示注入全部。用户可用 `/日记范围` 自己覆盖。
- **注入日记的最大字符数**：默认 8000。防炸上下文保险丝——即使用户要求注入全部日记，
  总量超过该值也会优先保留最近的、截断更旧的并在注入文本中注明。
  估算：中文为主时 8000 字约 **6400 tokens**（改进版估算；旧公式约 4400），占 60000 窗口约 11%（旧公式约 7%）；
  默认注入 7 天通常约 3500~6300 字，8000 一般够用；模型窗口较小可降到 5000~6000。
  （本项限制的是**注入到上下文的日记总字数**，不是单篇日记长度；单篇长度由提示词要求 500~900 字。）
- **群聊注入过滤**：默认开启。在群聊的新上下文中只注入"写于群聊"的日记片段，私聊写下的片段不进群聊；
  反向不限（群聊片段在私聊照常注入）。无场景标记的旧日记片段视为私聊来源、不注入群聊。
  某天若全是私聊片段，该天整天跳过并在注入文本中注明。
- **注入持久化**：默认关闭。关闭时日记只在每个新会话的第一轮请求注入一次（省 token，
  但她只在生成第一条回复时记得日记细节）；开启后每轮请求都把日记放进 system prompt，
  她全程都能回忆日记内容，代价是每轮都消耗日记的 token。

### 8.6 写作

- **每天定时自动写完整日记**：默认关闭。详见「每天定时自动写完整日记」一节。
- **自动写日记时间**：默认 22:00，24 小时制 `HH:MM`，按「日记时区」计算；仅上一项开启后生效。
  格式不对时不会自动写并记日志；bot 启动/重启晚于该时间超过 2 分钟不补写。
- **无新素材时写拟人日常**：默认开启。用户要求写日记但距上次没有任何新对话时，
  她会写一段自己的拟人生活随笔（明确标注、不含用户画像）；关闭后直接提示没有新内容、不写。
  素材过少也不会硬凑完整篇：没有新素材、也没有可合并的未吸收简记时，`/日记 完整` 会退化为
  "她的日常随笔"（每天最多一篇，不占完整名额）；有未吸收简记时才会合并成完整篇并占名额。
- **每个场景每天最多几篇完整日记**：默认 1；0 表示不限制。
  ⚠ **完整日记是“质量锚点”，强烈不建议把每日上限设多**：默认每场景每天 1 篇即可。
  完整篇用于沉淀用户画像与评价（500~900 字），写多了会稀释质量、增加 token 与阅读负担；
  日常小更新用默认的**简记**更合适。仅在 token 非常充足且确有需要时才调到 2 或更高，
  0（不限）只建议在明确知道自己需要时使用。
  按场景计算：私聊和群聊各自独立（群与群目前不隔离），简记/随笔不占额度。
  该名额会被**所有写完整日记的路径**占用：手动 `/日记 完整`、哨兵 90% 自动写、每天定时自动写；
  哨兵撞上限会**自动降级为简记**（保证记忆不断档），手动撞上限会直接拒绝；每天次日 00:00（按「日记时区」）重置。
  `/日记 完整` 成功后会提示"已写 X/N、还剩 Y 篇、次日 00:00 重置"。
- **写日记时读取的最大消息条数**：默认 60。有素材游标时只读"上次写日记之后"的全部新消息；
  游标失效（reset/历史压缩）时才回退最近 N 条。条数与写日记时**一次性**消耗的 token 成正比，但量不大。
- **群聊素材倍率**：默认 3。群聊历史混有其他成员发言（且历史不带发送者 ID、无法按人过滤），
  游标失效回退时实际读取 = 最大条数 × 倍率，提高覆盖到画像对象本人发言的概率；私聊不受影响。
- **手动写日记的最低上下文占用**：默认 0（不限制）。设成如 0.5 后，上下文占用未过半时 `/日记` 会被婉拒；
  哨兵自动写日记不受此限。
- **写日记的附加要求**：自定义追加到写作提示词的要求（如语气、格式偏好）。

### 8.7 隐私与安全

- **允许使用插件的用户（白名单，v0.5.5 新增）**：填 sender_id（QQ 号等），用逗号、空格或换行分隔；
  **留空表示所有人都能用（默认）**。填了之后：名单外的人发日记指令会被静默忽略，
  也不会被注入日记、不会被哨兵自动写日记、不会出现在每天定时自动写日记的名单里。
  私聊和群聊统一按这份名单过滤；Web 日记本页面不受影响（本来就只有管理员能看）。
  典型用法：机器人在群里服役，但只想让 AI 给你一个人写日记——填你自己的 QQ 号即可。
- **写完后展示日记全文**：默认关闭，她只用正常口吻告知日记已写好；开启后会在告知后附上全文（仅私聊生效）。

### 8.8 反馈风格

- **人设口吻**：默认开启，读取当前会话的人设（含 `/persona` 切换的人设），
  **尽可能多的指令反馈都改用她的性格与口吻输出**：写日记与写完后的口头告知；`/记一下` 的记下确认；
  备忘、查看日记、删除日记的确认/拒绝/取消/超时反馈；`/导出日记` 与 `/导入日记` 的流程反馈；
  `/日记密码` 的结果与拒绝；`/日记范围` 与 `/注入日记` 的确认；上下文哨兵的提醒与自动写完告知；
  每天定时自动写日记的写完告知。**列表、日期清单、帮助菜单、日记状态、日记正文，
  以及保存失败/验签失败/密钥不可用等技术报错保持固定文案**（保证数字、日期、指令与诊断信息逐字准确）；
  关闭后全部使用固定文案，不额外调用模型。完整覆盖清单见本节末尾「人设口吻的覆盖范围与边界」。

### 8.9 群聊行为

- **群里只响应@我的指令**：默认关闭。开启后群里不带@的日记指令一律无视，彻底杜绝多 AI 抢答；
  点名请用 QQ 自带@（v0.5.5 起文本手敲 @名字 不再生效）。

### 8.10 限额与防护

- **日记操作间隔（分钟）**：默认 5，每个用户两次**手动**写日记/删日记的最小间隔；0 为不限制，最高 60。
  查看、哨兵自动写、每天定时自动写都不受此限；冷却内反复发 `/日记 完整` 会被婉拒（优先于其它判定）。

### 8.11 杂项

- **（已废弃）启用上下文哨兵**：配置页「杂项」组第一条的兼容项，用来接住 v0.5.4 及更早的旧配置——
  旧配置里是 `false` 时，本插件会把两档阈值都当成 0（哨兵停用）并记一次迁移日志。
  新用户不用管它；想重新启用哨兵就改为 `true`，再到上方「上下文哨兵」调两档阈值。
- **日记本页面的称呼**：默认 TA。管理面板「日记本」视图左上角显示为「XX的日记本」，留空回退 TA，最长 12 个字符。
- **日记时区**：默认 Asia/Shanghai。写日记的时间戳、按天归档、"最近 N 天"的计算都用这个时区；
  填 IANA 时区名（如 `Asia/Tokyo`），留空跟随服务器本地时间，填错会回退本地并记日志。

### 8.12 多用户与隐私

- 日记按**用户**（发送者 ID）完全隔离：谁下指令写的就是谁的画像，各自保存、各自注入，互不影响。
- 群聊里写日记时，会在写作提示中声明"记录来自群聊、可能包含其他成员发言"，要求只围绕画像对象本人来写。
- `/查看日记` **仅私聊可用**，在群里使用会被拒绝，日记内容不会出现在群消息里。
- "写完后展示日记全文"只在私聊生效，群聊中即使开启也只口头告知、不展示全文。
- **注入按会话场景过滤（方向性）**：每个日记片段的分隔条都带"写于私聊 / 写于群聊"标注。
  在群聊的新上下文中只注入群聊来源的片段——私聊里的悄悄话不会顺着日记被带进群里；
  反过来，群聊来源的片段在私聊中照常注入（配置"群聊注入过滤"可关）。
  注意：这意味着她在群里可能"只知道群里的事"，表现会和私聊略有差异，这是设计使然。
- **群与群之间不隔离（设计边界，请知悉）**：隔离只分"私聊/群聊"两个场景，不区分具体哪个群。
  A 群写下的群聊日记片段，在你和 AI 同在的 B 群也可能被注入；A 群的群聊备忘也可能在 B 群写日记时被吸收。
  如果你和她在多个群里相处，请把"所有群聊"当成一个共享场景来理解。
- **备忘同样按场景隔离**：`/记一下` 存的备忘带场景标签，私聊写日记吸收全部备忘，
  群聊写日记只吸收群聊备忘（私聊备忘继续等待，不会出现在群聊来源的日记片段里）；无场景标记的旧备忘视为私聊来源。
- 每个用户只能查看 / 删除自己的日记，无法访问他人的。
- **`/导出日记` 只能导出自己的**：插件按发起指令的发送者 QQ 号派生并读取其专属日记文件，
  迁移包也只通过私聊文件发给该发送者；群里发会被拒绝；指令后面带 `@别人` 或其它参数会被忽略
  （不会用来指定别人的日记）；包内只有本人的派生钥匙，别的用户钥匙无法验证/伪造这份签名，
  转发给别人也会因"主人 QQ 不一致"被导入拒绝。**管理面板「日记本」页的导出是管理员权限**，
  可以导出任意用户的日记（该用户设了查看密码时需先输入密码）——这与 QQ 指令侧的"只能导出自己"不是同一权限层级。
- **定时自动写日记的用户表**：`auto_diary_users.json` 只保存私聊会话的发送者 ID、UMO 与昵称，
  仅用于到点写日记和主动通知；`auto_diary_state.json` 只保存当天是否已触发。
  两者都在插件数据目录，不进入日记 zip/迁移包，也不参与注入；停用功能后不需要可手动删除，
  插件下次启动会按已有私聊会话重新补齐。
- **token 校准数据**：`token_calibration.json` 只保存各 provider::model 的数字系数、样本数与更新时间，
  不含任何聊天内容。
- **日记防篡改**：每篇日记保存时生成 HMAC-SHA256 签名（绑定用户+篇目名+内容），读取时验签。
  签名钥匙一人一把，由主密钥 `.diary_key` 按 QQ 号派生（v0.4.0 起；此前直接用主密钥签名，
  旧日记读取时自动回退验签、下次写入自动升级）。任何在插件之外的修改都会被判定失效——不查看、不注入，
  只有她写的日记才会被使用。注意：**验签失败时插件会拒绝整次写入**（不会把被改过的内容重新签成"合法"），
  请先删除该篇或恢复备份；签名密钥 `.diary_key` 不可读时同样拒绝写入。
- **数据去向**：写日记、注入日记、人设化反馈都会把**相关对话内容**交给你在 AstrBot 里配置的模型服务
  （provider，由你自行选择与配置）；插件本身不额外联网，不上传日记、密钥或任何数据到作者或第三方服务器。
  所有日记、密钥、偏好文件都只落在本机插件数据目录。

### 8.13 人设口吻的覆盖范围与边界

「人设口吻」（配置项 `use_persona`，默认开启）会读取**当前会话**的人设
（含用 `/persona` 切换的人设；会话没指定时回退到默认人格），
让模型把指令的**对话式反馈**用自己的性格与口吻重说一遍再发给你。每一处生成提示词都会明确要求
"必须保留"其中的数字、日期、条数与指令写法；模型写偏或不可用时，自动退回原来的固定文案。
目标是在不牺牲数据准确性的前提下，让她的口吻覆盖尽可能多的指令反馈。

**一、全句人设化的场景（按指令分组）**

| 指令 | 哪些反馈会用人设口吻 |
| --- | --- |
| `/日记`（写日记） | 写完后的口头告知；操作冷却的婉拒；上下文占用未达门槛的婉拒；没有新素材 / 今天的随笔已写过之类的对话式拒绝 |
| `/记一下`（写备忘） | 记下成功的确认（保留原话引用与待写条数；场景说明仍固定追加）；保存失败保持固定文案 |
| `/查看备忘` `/删除备忘` | 群聊拒绝；查看时没有待写入的备忘 / 删除时没有可删的备忘；删除一条 / 清空全部 / 取消 / 回复看不懂导致的取消（人设化告知已取消）/ 序号不存在（保留当前条数） |
| `/查看日记` | 群聊拒绝；还没有写过日记；取消查看；超时；所选日期没有日记；验签失败 / 被篡改的诊断提示保持固定文案；回复看不懂或序号越界时只给固定用法提示并**继续等待**（不取消、不人设化） |
| `/删除日记` | 群聊拒绝；还没有日记；操作冷却的婉拒；取消删除（含删除全部时在二次确认环节放弃）；删除成功（保留天数与日期列表）；全部删除完成；超时；日期或时间段合法但查不到日记（人设化告知后结束等待）；序号越界或回复看不懂时只给固定用法提示并**继续等待**（不人设化、不取消）；删除失败（权限 / IO）为固定文案 |
| `/导出日记` | 群聊拒绝；还没有日记可导出；打包完成告知（保留天数与钥匙提醒）；迁移包已发出告知 |
| `/导入日记` | 群聊拒绝；请把迁移包作为「文件」发来的提示（保留「文件」「120 秒」「取消」）；取消导入；没收到文件；文件下载失败；导入成功（保留天数与签名方式）；导入被拒绝（原因原样保留）；导入超时 |
| `/日记密码` | 群聊拒绝；设置 / 修改 / 取消的结果告知；已设置过、未设置过、旧密码不对、新密码不合规（保留 4~32 位、不含空格的要求）、本来没有密码却要取消、取消时密码不对等拒绝反馈（无参查看状态与用法、保存失败保持固定） |
| `/日记范围` | 设置成功的确认（保留范围描述与"下次 /reset 后生效"）；无参查看当前设置、"没看懂～可选…"用法提示、保存失败保持固定 |
| `/注入日记` | 还没有日记可注入；指定范围里没有日记（保留范围描述）；本会话都读过了、没有新篇目的告知；注入确认（保留日期清单）；无参用法与"没看懂"提示保持固定（本指令无等待式交互） |
| 上下文哨兵 | 占用达到提醒阈值时的提醒；上下文将满但本轮没有新素材可写的警告（都保留百分比、`used/limit` tokens 与 `/reset`、`/日记` 等指令写法）；自动写日记完成后的告知（`used/limit` 的提示行保持固定格式，告知正文用人设口吻） |
| 每天定时自动写日记 | 写完后主动私聊的人设口吻告知；写入失败时只发一次固定技术说明（不重试，保留原因与 `/日记` 指引） |

> 人设化只改**措辞**，不改判定：冷却、门槛、权限、删除与注入逻辑仍按固定规则执行，
> 反馈里的事实由插件在提示词中给定，不是让模型自行回忆。

**二、只用固定文案 / 固定正文的场景**

| 场景 | 具体内容 | 为什么保持固定 |
| --- | --- | --- |
| 列表与数据 | 日记日期清单、备忘清单、`/日记状态` 的数字、帮助菜单、无参数时的设置与用法、用法示例与"没看懂～…"指引 | 数字、日期、指令语法必须逐字准确，转述容易漏项或改错格式 |
| 日记正文 | `/查看日记` 读出的日记全文、写完后展示的全文、注入给模型的日记内容、导出包里的日记 | 日记原文必须原样，不能被二次创作或摘要 |
| 技术 / 安全诊断 | 密钥不可读、验签失败、zip 损坏、保存失败 / 权限失败、导出文件发送失败、自动写日记失败、导入 / 导出的兜底失败提示、环境不支持交互 | 诊断信息是排查线索，必须以固定措辞、原样原因给出，不能让模型"友好化"后失真 |
| 安全提示 | 删除全部日记的二次确认 | 二次确认是安全闸门，措辞必须固定、明确，不能被改写弱化 |
| 保存失败告知 | `/记一下`、`/日记密码`、`/日记范围` 的保存失败（数据目录不可写或磁盘已满） | 必须明确"没有改动"，不能让口吻化掩盖写入失败 |

**三、开关关闭与生成失败时的回退**

- **关闭「人设口吻」**（`use_persona=false`）：所有指令反馈直接使用固定文案，**不会额外调用 LLM**
  （不增加 token 消耗，也不增加响应延迟），输出与未开启时逐字一致。
- **开启但本次生成失败**：没有可用模型、调用报错、返回空，或当前会话与默认人格都取不到人设文案时，
  自动回退到同一处的固定文案——指令照常完成，不会因为模型抽风而失败。
- **回退只影响措辞**：无论走人设还是固定文案，删除、保存、注入等结果完全一致；
  数字、日期、指令与技术诊断在两种路径下都保持准确。

## 9 标准使用流程（SOP）

**第一步：部署与初始化（管理员，只做一次）**

1. 安装插件并在 WebUI 重载（见「安装」一节）；
2. 把"模型上下文窗口"填成你实际模型的上限（如 DeepSeek-V3 填 60000），
   并确认 AstrBot 的"最大上下文消息数"没有设得太小——否则历史会在到达阈值前被 AstrBot 自己截断，哨兵就失效了；
3. 按需调整阈值与间隔（默认值适合大多数场景，可以先不动）；
   不想让插件服务所有人时，在「允许使用插件的用户」填白名单；
4. 如果群里有多个 AI 都装了本插件：建议每个实例都开启"群里只响应@我的指令"，点名用 QQ 自带@。

**第二步：日常使用（用户，一个记忆周期）**

1. **正常聊天**，什么都不用管——哨兵在后台静默估算上下文占用；
2. 聊天中想到什么必须记住的事，随时发 `/记一下 内容`，她会存成备忘；
3. 上下文用到约 75% 时，她会提醒一次"快到写日记的时候啦"——这是信号：**把还没说的重要事说完**；
4. 用到约 90% 时她会自动写好**完整日记**（也可以随时主动发 `/日记` 写简记；觉得重要就发 `/日记 完整`），
   写完用平时的口吻告诉你一声；
5. 发 `/reset` 开启新上下文——她会先自动读最近 7 天的日记，再接着陪你，记忆无缝衔接
   （注入发生在 reset 后第一句正常对话时；命令消息不触发也不妨碍注入，
   不确定有没有注入成功可以发 `/日记状态` 看"本会话日记注入"一栏）；
6. 回到第 1 步，开始下一个周期。

**第三步：查看与维护（按需）**

- 用户：私聊 `/查看日记` 看自己的日记，私聊 `/删除日记` 清理，`/日记范围` 调整每次注入多少，
  `/日记状态` 看占用与篇数；
- 管理员：定期在日记本页面点「备份全部日记」或「备份全部日记并打开位置」
  （**并另外妥善保存主密钥 `.diary_key`**，两者缺一不可，详见「日记存储位置与提取」）；
  用户换设备取日记让他自己发 `/导出日记` 即可（QQ 直发、含本人派生签名钥匙、可跨设备迁移）。

## 10 安装

- **源码 / Docker 部署**：将整个 `astrbot_plugin_memory_diary` 文件夹放入 AstrBot 的 `data/plugins/` 目录；
- **AstrBot Launcher（Windows）**：放入对应实例的 `...\instances\<实例UUID>\core\data\plugins\`；
- 也可以在 WebUI 插件页直接上传 `astrbot_plugin_memory_diary.zip` 安装。

放好后在 WebUI 插件页重载即可。要求 AstrBot >= v4.0.0。

> **从 v0.5.4 升级（兼容性与连续性）**
>
> - **不需要迁移数据**：日记格式仍是"按天归档 v3"，目录结构、`diary_*.zip` 文件名派生、
>   签名算法与 `.diary_key` 主密钥派生方式均未变。v0.5.4 写下的日记 v0.5.5 可直接读取、验签、续写；
>   反过来 v0.5.4 也能读回 v0.5.5 续写的内容（双向兼容由回归测试实际验证）。
> - **旧配置直接可用**：v0.5.5 新增的配置键没填就使用默认值；已删除的 `bot_call_names` 会被忽略；
>   `enable_context_watch` 保留为兼容项，旧配置里的 `false` 会迁移为"两档阈值 0（哨兵停用）"并记一次日志。
> - **默认行为变化（升级后可能感知）**：①「改进版 token 估算 / 自动校准」为实验性功能、默认关闭
>   （哨兵暂时按旧公式估算，想更准可到配置页开启）；② 正式日记小标题改为由人设自由起名，旧日记仍合法可读；
>   ③ 群聊 @ 规则、零宽字符容错、`/日记状态` 群聊隐私等有少量行为调整（详见 CHANGELOG）。
>   旧配置文件中**已保存的值不会被改写**，只补缺失的默认项。
> - **升级建议**：先备份数据目录（或「备份全部日记」+ `.diary_key`），再覆盖安装/重载插件即可，无需清空数据。

> **部署方式建议**：本地部署（Windows 桌面客户端 / Launcher / 本机源码）和云端部署均可；
> 云端取日记请用 `/导出日记` 或日记本页面导出，无需 SSH。

> **云端 / Docker 部署注意**：
> - `/导出日记` 的 QQ 文件直发，依赖协议端（NapCat）能读到 AstrBot 数据目录里的临时迁移包。
>   同机、同容器或**共享卷**部署可以直接用；如果 AstrBot 与 NapCat 分属两个**没有共享卷**的容器，
>   会提示"包打好了但发送失败（协议端可能读不到这个文件路径）"——给两个容器挂同一个数据卷
>   （挂到相同路径），或改用管理面板「日记本」页的导出（浏览器下载，不依赖协议端读文件）。
> - `/导入日记` 不受共享卷限制：文件由 QQ 协议端上传、AstrBot 侧下载到本地临时文件后验签安放。
> - 换云端服务器：新实例装好插件并**启动一次**（让本机生成自己的 `.diary_key`），再让用户发
>   `/导入日记`；两边主密钥不同时会自动重签共存（resign），不影响新服务器上其他用户的日记。
>   如果直接搬整个插件数据目录，则必须连 `.diary_key` 一起带（见「日记存储位置与提取」）。
> - 插件目前声明支持 `aiocqhttp`（NapCat 等）；其他协议端能否收发文件，取决于其 File 组件实现。

## 11 日记存储位置与提取

### 11.1 两种备份通道的分工（先选对工具）

| | 一键备份包（v0.5.5 新增） | 单用户迁移包（`/导出日记`） |
| --- | --- | --- |
| 内容 | **全部用户**的日记 zip + `备份说明.txt` | **单个用户**的全部日记 + 该用户的派生签名钥匙 |
| 含签名钥匙？ | **绝不含任何钥匙**（安全设计） | 含本人派生钥匙（泄露也只动得了这一份） |
| 适用场景 | 管理员定期整机备份、整台服务器迁移 | 用户自助换设备、单用户恢复 |
| 恢复前提 | **必须连同主密钥 `.diary_key` 一起迁移**，验签才通过 | 不需要主密钥：导入时自动用本机钥匙重签安放 |
| 入口 | 日记本页面导出菜单「备份全部日记」（浏览器下载）/「备份全部日记并打开位置」（本机面板） | QQ 私聊 `/导出日记`；或日记本页面选中用户导出 |

为什么备份包刻意不带钥匙：每个用户的签名钥匙由主密钥 `.diary_key` 做 **HMAC-SHA256 确定性派生**
（`HMAC-SHA256(主密钥, "user-key:<QQ号>")`，与「备份全部日记」包内 `备份说明.txt` 的口径一致）——
新机只要有同一把主密钥，所有派生钥匙自动重算，
旧日记验签照常通过；而主密钥能签发**所有人**的日记，泄露面远大于日记内容本身，
浏览器下载的备份包比服务器目录更易外泄，所以钥匙绝不入包。

**恢复路径**：

- 备份包 + 主密钥一起带到新机 → 全部验签通过，一切照常；
- 只有备份包、主密钥丢了，但**旧机还能用** → 让用户在旧机发 `/导出日记` 生成带派生钥匙的
  迁移包，到新机 `/导入日记` 自动重签，验签恢复；
- 只有备份包、主密钥丢了、**旧机也没了** → 插件无法再通过验签（防篡改设计，不是故障）；
  日记 zip 本身未加密，可以解压出 `.md` 纯文本自行阅读或喂给任意 AI，
  但插件不会再把它们当合法日记。所以：**备份日记的同时，务必单独备份 `.diary_key`**。

> **备份包不包含损坏隔离副本**：日记 zip 损坏时，插件会把原文件改名成
> `*.corrupt-<时间戳>.zip` 隔离并留在插件数据目录里（不会覆盖、也不会写进备份包）——
> 一键备份只打包正常的 `diary_*.zip`。如果要把损坏文件留作排查证据，请手动从数据目录拷走。

### 11.2 本地部署（Windows 桌面 / Launcher / 本机源码）

插件用的是 **AstrBot 的插件数据目录**，不是插件安装目录。实际路径是：

```text
<AstrBot 数据根>/plugin_data/astrbot_plugin_memory_diary/
```

"数据根"按部署方式不同：

| 部署方式 | AstrBot 数据根 |
| --- | --- |
| 设置了 `ASTRBOT_ROOT` | `$ASTRBOT_ROOT/data` |
| AstrBot 桌面客户端 | `~/.astrbot/data` |
| **AstrBot Launcher（Windows）** | `~/.astrbot_launcher/instances/<实例UUID>/core/data` |
| 源码 / Docker | 启动时工作目录下的 `data` |

Windows Launcher 的实际例子：

```text
C:\Users\<用户名>\.astrbot_launcher\instances\<实例UUID>\core\data\plugin_data\astrbot_plugin_memory_diary
```

注意这里是 `instances\<UUID>\core\data`，不是 `C:\Users\<用户名>\.astrbot\data`，也不是 AstrBot 安装目录下的 `data`。

**Windows 一键定位并打开（推荐）**

不记得路径、不想一层层翻目录时，把下面这段**整体复制粘贴到 PowerShell 窗口**，回车等几秒：
它会递归搜索当前用户目录下所有 `diary_*.zip`，取最近修改的一个，把完整路径复制到剪贴板，并直接打开所在文件夹：

```powershell
$f = Get-ChildItem "$env:USERPROFILE" -Recurse -Filter "diary_*.zip" -ErrorAction SilentlyContinue |
     Sort-Object LastWriteTime -Descending |
     Select-Object -First 1

if ($f) {
    $f.FullName | Set-Clipboard
    Write-Host "已复制完整路径：" $f.FullName
    explorer $f.DirectoryName
} else {
    Write-Host "没找到 diary_*.zip：可能不是 Windows Launcher 部署，或 AstrBot 不在当前用户目录下。"
}
```

- 普通 Launcher 单实例用户：用这段就够了，打开的文件夹里 `diary_*.zip`、`.diary_key` 都在；
- **多用户/多实例**：它定位的是"最近写过日记"的那个实例目录；想精确定位某个实例，先按下方
  "Launcher 的实例 UUID 怎么查"确认 UUID 再走精确路径；
- `.corrupt-<时间戳>.zip` 损坏备份也符合 `diary_*.zip` 命名，可能排在最前——打开文件夹后注意辨认。

**Launcher 的实例 UUID 怎么查？**

Launcher 的每个实例就是 `instances` 下的一个文件夹，文件夹名就是 UUID：

```powershell
Get-ChildItem "$env:USERPROFILE\.astrbot_launcher\instances" -Directory |
    Select-Object Name, LastWriteTime
```

如果分不清哪个是正在用的实例，可以看正在运行的 AstrBot 进程路径，里面会带实例 UUID：

```powershell
Get-CimInstance Win32_Process |
    Where-Object { $_.ExecutablePath -like "*\.astrbot_launcher\instances\*" } |
    Select-Object -ExpandProperty ExecutablePath
```

路径里的 `instances\<这一串>\venv\...` 就是实例 UUID。只有一个实例文件夹时，直接用那个即可；
Launcher 界面如果显示了实例 ID，也可以直接对照。

**找不到 zip 时，先确认它是"还没写"还是"找错目录"：**

- zip 是第一次成功写日记后才创建的。目录里只有 `.diary_key`、没有 `diary_*.zip`，可能是还没写成功，不一定是路径错。
- 文件名是 `diary_<16位哈希>.zip`，一个用户一个，不叫 `日记.zip`。
- `.diary_key` 是隐藏文件；`说明.txt` 在 zip 里面，不在目录根下。

### 11.3 云端部署（Docker / Linux 服务器）

- **取回日记**：优先用插件内通道——用户私聊 `/导出日记`（QQ 直发），或管理员在日记本页面
  「下载到浏览器」/「备份全部日记」。浏览器下载不依赖 SSH，也不要求协议端能读服务器文件。
  若管理面板就开在服务器本机（非远程访问），也可以用「**备份全部日记并打开位置**」直接存到

  打不开，这时请用浏览器下载。

#### 11.3.1 主密钥 `.diary_key` 长什么样

- **位置**：数据目录下（`.../plugin_data/astrbot_plugin_memory_diary/.diary_key`），是隐藏文件，
  Linux 上 `ls -la` 才能看到；Windows 资源管理器需要勾选"显示隐藏的项目"。
- **内容**：**一行 64 位小写十六进制字符**（32 字节随机数，形如 `^[0-9a-f]{64}$`），
  没有前缀、没有引号、不是 JSON、不是 zip；文件权限通常为 `0600`（仅属主可读写）。
  读取时插件会 `strip()` 掉首尾空白，所以末尾多一个换行也能用，但建议保持原样。
- **生成时机**：第一次需要签名时（首次成功写日记、首次导出/验签）自动生成，启动时不一定存在。
- ⚠ **不要手造、也不要拿别的实例的 key 顶替旧 key**：日记文件名和每篇签名都由它派生。
  换了 key，旧 `diary_*.zip` 会变成插件找不到的孤儿文件、验签全部失败（这是防篡改设计，不是故障）。

#### 11.3.2 怎么提取与校验

Docker（容器名与数据目录用上面的 `find` 结果替换）：

```bash
docker cp <容器名>:/AstrBot/data/plugin_data/astrbot_plugin_memory_diary/.diary_key ./diary_key.bak
# 或者直接看内容
docker exec -it <容器名> sh -lc 'cat /AstrBot/data/plugin_data/astrbot_plugin_memory_diary/.diary_key'
```

Linux 源码部署：

```bash

```

拷出后自检（64 个十六进制字符）：

```bash
wc -c < diary_key.bak                      # 正常应为 64（若编辑器补了换行可能是 65）
grep -Eq '^[0-9a-f]{64}$' diary_key.bak && echo "key OK"
```

Windows / Launcher 本机：直接到
`AstrBot\data\plugin_data\astrbot_plugin_memory_diary\` 复制 `.diary_key`（见 11.2 的目录打开方式）。
**插件刻意不提供 Web 下载主密钥**——它等于全部用户日记的签名权，只走服务器文件通道。

#### 11.3.3 和日记一起正确迁移（整机搬迁步骤）

1. **旧机**：日记本页面点「备份全部日记」得到 `memory_diary_backup_*.zip`；另把 `.diary_key`
   拷出（按 11.3.2 校验）。两样都要留，缺一不可。
2. **新机**：装好插件、**先停掉/别启动**，确认数据目录
   `.../plugin_data/astrbot_plugin_memory_diary/`。
3. 若新机已经自动生成过 `.diary_key`（第一次写日记/导出后就会出现）：**先备份或删除它**，
   不要新旧 key 混用。然后把旧机的 `.diary_key` 放进该目录（POSIX 建议 `chmod 600`）。
   替代做法：把旧 key 文本原样存为 `diary_key.txt` 放进数据目录——插件启动时若发现本机
   **还没有** `.diary_key`，会自动收养它并改名为 `.diary_key`。
4. 把备份包里的 `diary_<哈希>.zip` 解压/拷贝到数据目录根下，**保持文件名不变**（不要解压 zip 内部）。
5. 启动/重载插件：`/日记状态` 或日记本页面应能看到原有日记；验签通过即迁移成功。
6. **只迁一个用户**不需要主密钥：让用户在旧机发 `/导出日记`（迁移包含派生钥匙），
   新机发 `/导入日记` 自动重签；主密钥只在"整机/全部用户"迁移时需要。

> 安全提醒：`.diary_key` 不要放进备份包、不要发聊天/公开网盘——拿到它就能签发**所有人**的日记；
> 备份包本身不含钥匙，正是为了降低"浏览器下载物外泄"的风险。

### 11.4 目录结构

```
├── .diary_key                  ← HMAC 主密钥（随机生成，各用户签名钥匙由它派生；留在 zip 外，备份/迁移务必带上）
├── diary_<用户ID哈希>.zip      ← 每个用户一个 zip，按天归档、分文件夹
│     ├── diaries/20261023.md   某一天的日记（当天多篇追加在同一文件，带时间分隔）
│     ├── sigs/20261023.sig     当天日记的防篡改签名（仅插件验签用，用户可忽略）
│     ├── diaries/20261024.md   又一天……
│     └── 说明.txt              日记结构、使用方法、存储位置
├── auto_diary_users.json       ← 每天定时自动写日记的私聊用户登记（QQ/UMO/昵称，仅用于写与主动通知）
├── auto_diary_state.json       ← 每天定时自动写日记当天是否已触发（防重复/失败不重试）
├── token_calibration.json      ← token 估算校准系数（按 provider::model 存数字，无聊天内容）
```

### 11.5 提取事项

- **跨设备迁移（换电脑/换服务器）**：整机搬迁用「备份全部日记」+ 带上 `.diary_key`；
  单用户迁移用 `/导出日记` + `/导入日记`，全程 QQ 内完成，签名自动重签，不用碰任何手动步骤。
- 想手动把日记发给某位用户**阅读**（不迁移插件数据）：直接把对应的 `diary_<哈希>.zip` 发过去即可，
  对方解压后挑需要的 `.md` 读，按 `说明.txt` 的指引可以喂给任何设备上的任何 AI。
- **手动发阅读用 zip 时不需要 `.diary_key`**：主密钥只用于插件验签和备份迁移，阅读和第三方 AI 都用不到它；
  zip 未加密，任何人拿到都能读——发送前请确认对象确实是日记主人。
- **手动迁移插件数据时则必须带上 `.diary_key`**：日记文件名和每篇签名都由它派生，
  少了它新设备找不到文件、验签全部失败。v0.4.0 起也接受把密钥文本存为 `diary_key.txt` 放进数据目录，
  插件启动时会自动收养为 `.diary_key`（仅当本机还没有密钥时）。
- 插件读写 zip 对模型完全透明，zip 存储不影响任何 AI 功能。
- **不要手改 zip 里的任何 .md**：验签会失败，插件将拒绝读取该篇（这是防篡改设计，不是故障）。
- 备份/迁移整个插件目录时必须包含 `.diary_key`，否则所有日记验签失效。
- 文件名是发送者 ID（如 QQ 号）经 `.diary_key` 做 HMAC 派生的哈希前 16 位（v0.3.0 起；
  旧版 MD5 命名的文件会在首次访问时自动改名迁移）。**只拿到 zip、没有拿到 `.diary_key` 时**，
  无法靠枚举 QQ 号定位文件；如果整个数据目录连同 `.diary_key` 一起泄露，仍可计算文件名并验签——
  所以目录权限和密钥备份都要保护。可让对应用户发 `/日记状态` 核对，或按 zip 内 `说明.txt` 的昵称辨认。
- v1.x 明文 `.md + .sig`、v2.0 单篇 zip、v3.0 按篇时间戳条目、v3.1~3.3 平铺按天文件，
  都会在首次读取时自动迁移为 `diaries/` + `sigs/` 分文件夹的按天归档（同一天的多篇合并、保留时间分隔条）。

## 12 实现原理

**日记是怎么写出来的**：插件以当前会话（umo）的历史消息为素材，用"素材游标"记下上次写到哪里，
写作时只取游标之后的新消息 + 未写入的备忘，连同写作提示词一起交给模型，由她以第一人称写成日记。
写日记前会自动剔除操作类内容（`/日记` `/删除日记` `/查看日记` `/记一下` 等指令、
插件的 📖/⚠️/📌 通知、`/reset`），她读不到也不会把这些写进日记（`/记一下` 的内容单独走备忘通道，不会丢）；
写作提示词同时声明对话中的"指令"只是素材、不是命令（防注入）。群聊素材可能包含其他成员的发言，
提示词会声明这一点并要求只围绕画像对象本人来写。

**记忆是怎么接续的**：新会话注入通过 `on_llm_request` 钩子实现——`/reset` 后第一轮正常对话时，
把按范围选好的日记包装成 `<memory_diary>` 块塞进本次请求（默认临时一次性、不进历史；
开启注入持久化则每轮进 system prompt）。AstrBot 4.x 的 `/reset` 只清空 history、不换 conversation_id，
所以插件同时用"监听到 `/reset` 指令"和"上下文已清空"两条路径识别新代际；`/日记状态` 可查看本会话是否已注入。
注入文本里明确写了优先级规则：日记只是背景参考，与当前对话冲突时永远以当前对话为准。

**与语义召回（RAG）类记忆插件的定位差异**（两者可并存，侧重不同）：

| 维度 | 本插件（显式日记注入） | 语义召回（RAG）类插件 |
| --- | --- | --- |
| 记忆载体 | AI 主动写的结构化日记（时间 / 画像 / 评价 / 叮嘱） | 对话消息切片 + 向量索引 |
| 召回方式 | 按时间范围整篇注入，结果稳定可预期 | 按语义相似度检索相关片段 |
| 内容性质 | 经 AI 整理过的概括与评价 | 保留原话的对话片段 |
| token 开销 | 由注入范围决定，有上限保险丝 | 由召回条数与片段长度决定 |
| 可解释性 | 可用 `/查看日记` 直接读到全文 | 通常可查看检索到的来源片段（视实现而定） |
| 适合场景 | 需要稳定的跨会话人格记忆与画像连续性 | 需要精确检索历史原话或较大知识库 |

简单说：本插件侧重"她主动记住了什么、怎么继续陪你"，语义召回侧重"按需检索哪段原话"；
两者关注点不同，也可以同时安装、各司其职。

**影响日记质量的因素**：模型本身的能力与人设（人设口吻会带进口吻）；
对话素材的量与质量（聊得太少写不出画像）；「写日记的附加要求」配置；
「写日记时读取的最大消息条数」与「群聊素材倍率」（游标失效回退时的取材窗口）；
群聊噪声（其他成员发言多时会稀释画像素材）。

**其他实现约定**：文件写入和消息发送都是一次尝试、失败会明确告知，不会重试轰炸；
验签失败、密钥不可用、文件损坏等安全相关失败会直接拒绝写入，不会降级绕过；
zip 和 `pref_*.json` 的写入都是"临时文件 + `os.replace`"原子操作。

## 13 故障与恢复

**遇到问题先做这两步**：绝大多数异常（配置没生效、指令行为不对、升级后行为异常）
都能通过在 WebUI **重载插件**解决；重载无效时**重装插件**（日记在数据目录，重装插件不丢日记）。
这两步做完再往下查。

- **`.corrupt-<时间戳>.zip` 文件**：插件发现日记 zip 损坏时，不会覆盖它，而是把原文件改名成这个备份并拒绝写入。
  原路径这时已经不存在了；请人工检查备份（可尝试用压缩软件修复），确认没有可恢复内容后直接删除该备份即可，
  下次写日记会新建。不要手改备份再放回，签名会失效。
- **"验签失败"提示**：日记文件在插件之外被手动修改过。想保留就先用 `/删除日记` 删掉那天或从备份恢复，
  否则她不会再读这篇，也不会在它基础上写新日记。
- **"签名密钥不可用"提示**：数据目录下的 `.diary_key` 丢失、为空或不可读。
  **先从未丢失的备份恢复，不要直接删掉让它重建**——v0.3.0 起的文件名也由这个密钥派生，
  重建后旧的 `diary_*.zip` 会变成插件找不到的孤儿文件，而且签名全部失效。
  只有确认旧日记都不要了，才手动清理旧 zip 后重建。
- **崩溃残留**：崩溃可能留下 `.tmp-<pid>` / `.tmp` 临时残骸，可以手动删；目标文件本身永远是完整的
  （原子写入，任何时刻要么是完整旧文件、要么是完整新文件）。

**常见问题**

- **为什么提醒我设的是 90%，到 92%（或 88%）才自动写？**
  占用百分比是**估算值**，与服务商真实计费存在误差。开启「token 估算自动校准」（实验性功能，默认关闭）后，
  插件会按真实用量自动修正系数、越用越准；`/日记状态` 的"校准"一行可以看到
  当前系数与样本数。估算偏差 ±15% 以内属正常，不必手动干预。
- **为什么她在群里不理我的指令？** 按顺序排查：群里发指令是否带了 QQ 自带@
  （或开启"群里只响应@我的指令"后忘了@）；你是否在「允许使用插件的用户」白名单外；
  消息是否被其他插件加了尾巴（v0.5.5 已自动剥离零宽字符；写日记/日记范围/注入日记/日记密码的
  "参数不认识"分支、`/记一下` 空内容、备忘/查看/删除的"没看懂"分支都会记带 `repr()` 的警告日志，
  可把日志发给作者）。
- **为什么 `/日记状态` 的占用和 AstrBot 面板显示的不一样？** 两者口径不同：
  插件估算的是"本插件哨兵判定用的上下文"（最近一次请求的估算，含系统提示词、工具等本插件看得到的部分），
  `/日记状态`、手动写日记门槛、哨兵三处用的是同一个数；AstrBot 面板的统计口径和插件不同，
  所以数字不必完全相等，以插件内的相对趋势为准即可。它是估算值，偏差 ±15% 左右正常，校准会随使用收敛。
